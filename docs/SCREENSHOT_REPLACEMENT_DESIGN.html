远程媒体处理 / 截图资料修复

截图替换的设计思路

先验证原图，保留有效截图，再由 NAS 补图。视频留在下载器端，主程序接收 Pixhost 图片链接；存在待确认问题时，任务停在发布之前。

适用位置：抓取、准备转种资料和发布前校验。已发布帖子中的图片修改，需要另做站点编辑适配与权限核验。

有效原图优先

达到校验门槛时直接沿用，避免重复截图与上传。

计算靠近视频

NAS 读取媒体并截帧，152 负责调度和资料管理。

不确定就待确认

图片数量、字幕状态和人工确认共同决定能否发布。

数据走向处理流程替换规则具体示例部署与配置验证范围
01

三个位置，各自承担一件事

沿用 PTNexus 的资料处理流程，在下载器所在的 Linux NAS 上增加一个可独立部署的 Docker 媒体代理。代理只开放受限的媒体处理接口。

控制与资料

152 主程序

校验原图、决定是否补图，发送媒体路径及截图请求，保存最终截图资料和审核状态。

→
读取与截帧

NAS 媒体代理

读取白名单中的视频，运行 FFmpeg / mpv、字幕检查和 MediaInfo，直接上传生成的截图。

→
图片托管

Pixhost

接收图片并返回图片地址。代理使用官方 HTTPS API，返回完整图片链接及 BBCode。

回传：图片 URL / BBCode → 152 合并资料 → 发布前再次核对当前记录
视频无需传到 152。 qB 仍通过自己的 API 提供下载器操作；媒体代理使用独立 Token，只承担媒体信息、截图与文件检查。
02

从原图校验到发布，共六步

  1. 提取并验证原图

    从资料中提取图片 URL，去掉重复字符串并校验图片可用性。已知失效的图片不会被最终合并流程重新带回来。

    有效截图至少 3 张本轮抓取直接保留有效原图，不调用截帧和上传。
    缺图、失效或不足 3 张留下仍有效的原图，进入媒体检查和补图。

  2. 定位视频，检查字幕

    主程序使用下载器对应的媒体路径；NAS 代理校验路径、文件与目录权限。字幕检查结果会影响是否需要人工确认。

  3. 按运行方式生成截图

    后台抓取在可处理时生成正式截图，默认目标为 5 张；字幕未知或检查失败仍会标为待确认。交互式流程可先展示候选预览，由用户选择。

  4. 上传到 Pixhost，接收成功结果

    NAS 直接上传成功截取的图片，返回 URL 和 BBCode。部分成功时保留成功图片；全部失败则按失败处理。

  5. 合并并更新截图资料

    把有效旧图放在前面，再接入成功的新图，按完整 URL 字符串去重。用合并后的截图字段更新资料，不把整个简介重新覆盖一遍。

  6. 审核状态与发布门槛共同检查

    待确认、未知状态或图片不足会阻止自动发布。用户在原生资料页确认后，另行重试任务；已有确认资料会复用。排队、准备发布和实际上传前都检查当前资料，防止旧截图覆盖后续修改。

“正式截图 5 张”与“候选预览”是两个步骤。候选预览默认生成 12 个候选位置，供用户选择；不能把预览数量当作最终上传数量。

03

什么时候替换，什么时候停下

原图校验通过且 ≥ 3 张
保留有效原图，跳过本轮自动补图。发布环节仍读取当前审核记录。
只剩 1～2 张有效原图
保留这些图并尝试补图。合并后不足 3 张时，后台抓取标记为待确认。
原图全部失效
尝试生成新图；如果补图也失败，清空已知失效的截图资料并标为待确认。
字幕不能确认 / 检查失败
后台可继续尝试出图，但结果保留待确认状态；截图再多也不能直接跳过人工确认。
截图或上传部分失败
保留成功结果与有效旧图，再结合最终数量和字幕状态判断；“目标 5 张”不代表一定成功 5 张。
用户已明确确认
自动发布允许至少 1 张格式合规的截图 URL；0 张始终拒绝。确认动作本身不会自动发种，需要再重试任务。
两种校验分开理解。 抓取修复阶段检查原图可用性；自动发布关卡重新检查审核状态、去重后的 URL 格式和数量、来源标识以及当前资料一致性，不会在每次发布前重新请求全部图片来证明实时可用。

05

落地方式：NAS 一个容器，下载器一组配置

NAS 侧

  • 使用 Linux amd64 或 arm64 Docker 镜像；本版范围为 64 位架构。
  • 显式配置媒体目录和绝对路径白名单，目录只读挂载。
  • 设置独立 PTMOVE_PROXY_TOKEN，至少 32 字符。
  • Compose 示例默认绑定 127.0.0.1:19090；152 跨机器访问需配置可信网络或隧道。

主程序侧

  • 在“设置 → 下载器”启用远程媒体处理，明确填写实际代理端口及 Token。
  • 开启仅媒体代理，qB 列表和控制继续直连自己的 API。
  • 代理沿用下载器主机名加代理端口连接，需要为该地址安排可达通道。
  • 先验证预览、截图和字幕确认，再接入真实自动化任务。

路径一致是关键

以 qB 返回的文件路径为准。假设它看到 /volume1/downloads/Movie/Movie.mkv，媒体代理也应能从这个绝对路径读取文件。

qB 返回路径：     /volume1/downloads/Movie/Movie.mkv
代理容器内路径：  /volume1/downloads/Movie/Movie.mkv
允许的媒体根目录：/volume1/downloads

如果 qB 本身在 Docker 中，主机目录与 qB 容器目录可能不同。调整代理挂载的 source / target，使容器内路径和白名单匹配；不需要为这个示例移动正在使用的媒体文件。

代理的能力边界：非 root 运行、独立认证、限制请求字段和并发、拒绝路径穿越与符号链接越界。不挂载 Docker socket，不提供 qB 转发、任意命令执行或视频下载接口。
06

“暂存”分成 NAS 缓存与图床图片

NAS 临时截图

视频只读，生成的临时截图在任务结束后清理。媒体代理不负责删除原视频，也不接管 qB 的长期做种数据。

Pixhost 托管图片

上传结果是公共图床内容。本程序清理 NAS 临时目录不会删除 Pixhost 上的图片，也没有自动过期保证。程序保存的是图片 URL 和 BBCode。

实现与验证到哪一步

以下依据 v0.3.1 交付记录，验证日期为 2026-11-16；本文未重新访问服务器或真实站点。

已完成

  • 补图、资料合并、审核状态与自动发布保护已实现。
  • NAS amd64 / arm64 镜像已构建并验证镜像加载。
  • 合成视频的真实 FFmpeg / mpv 截图、预览、MediaInfo 已验证。

接入后验证

  • 真实 NAS 的地址、媒体目录、文件权限和网络通道。
  • 物理 ARM NAS 的媒体解码与运行表现。
  • 真实下载器、源站与目标站的完整下载和发种流程。
  • 已发布帖子图片的后续编辑不在本版自动修复流程内。
当前默认：自动化、月度计划和自动发布开关均默认关闭。安装代理后先做预览与截图验证，再按实际需求启用。
