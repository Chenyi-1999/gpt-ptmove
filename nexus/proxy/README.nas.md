# PTMove 0.3.1 NAS media agent

Reuses the native Go screenshot/subtitle/MediaInfo implementation. This package only exposes media operations; it does not export/download files, proxy qB, accept arbitrary commands or callbacks, or access the Docker socket. ISO mounting and BDInfo are unavailable. Extract discs into a media directory first. No privileged mode, host networking or extra capabilities are needed.

1. Copy `.env.example` to `.env`. Set `PTMOVE_MEDIA_SOURCE` to the absolute NAS media directory containing the downloader’s `save_path`, and set `PTMOVE_MEDIA_ROOTS` to a JSON array containing that same path (see `.env.example`). Set `PTMOVE_PROXY_TOKEN` to a random secret of at least 32 characters (for example generate one with `openssl rand -hex 32`). Never commit `.env`.
2. Run `docker compose -f compose.nas.yaml up -d --build` in this directory. Only the selected media directory is mounted, read-only, at its **identical absolute path** inside the container. For example, `PTMOVE_MEDIA_SOURCE=/volume1/downloads` and `PTMOVE_MEDIA_ROOTS='["/volume1/downloads"]'` keep qB’s `/volume1/downloads/...` save paths valid without changing qB configuration. The NAS user must permit UID/GID 65534 read access. If qB itself runs in Docker, use the absolute path it reports as the agent mount target, mapping the corresponding NAS host source; adjust the compose bind target and allowed roots together.
3. The host binding defaults to `127.0.0.1:19090`. Use a trusted VPN or SSH tunnel for a remote controller; changing `PTMOVE_BIND_IP` exposes the service on that interface. Bearer authentication requires a trusted encrypted network when crossing hosts. The downloader hostname is reused for the media-agent connection; a different host requires an appropriate tunnel/address arrangement.
4. In downloader settings enable remote mode, set the published port and independent proxy Token, and select **仅媒体代理**. qB list/statistics and publication checks continue directly against qB with its own credentials. Old configurations default to the original full proxy mode and may keep a blank proxy Token for existing legacy programs. Upgrading to this program requires selecting media-only mode and configuring its Token.

Startup fails unless both secret and allowed roots are configured. `PTMOVE_MEDIA_ROOTS` is a JSON array of existing absolute directories, e.g. `["/media","/archive"]` (Windows JSON paths must escape backslashes). Delimiters are deliberately unsupported. Root `/` is rejected. Paths must be absolute, cannot contain traversal or URLs, and canonical symlink targets must stay inside one of the roots; directory scans skip symlinks. Mount trusted media directories read-only and do not allow concurrent writers to replace path components with symlinks while processing.

Public health: `GET /api/health` gives only status/version/mode. All other requests require `Authorization: Bearer <PTMOVE_PROXY_TOKEN>`. Supported POST endpoints are `/api/media/screenshot`, `/api/media/mediainfo`, `/api/media/episode-count`, `/api/file/check`, `/api/file/batch-check`. JSON bodies are limited to 64 KiB; batch checks to 256 paths. Only one media request runs at a time (busy requests receive 429); capture/probe subprocesses have time limits. Screenshot modes inspect/preview do not upload; finalize accepts up to five selected times, default generation captures five. Preview count is capped at twelve. Subtitle confirmation/publication review stays in the controller.

Uploads use only `https://api.pixhost.to/images`, at most 10 MB per image, without external mirror fallbacks or automatic upload retries. Actual `show_url` and `th_url` are validated; the official show page supplies the real full-resolution URL when no image URL is returned. No `imgNN` host is invented. Resolution failure reports failure instead of silently saving thumbnails.

Offline checks: `go test ./...` (Go 1.25). Real-tool integration: set `PTMOVE_CAPTURE_INTEGRATION=1` then `go test -run TestCaptureIntegration -v .` inside a Go 1.25 environment with ffmpeg/mpv/mediainfo installed. The integration test generates a synthetic video in a temporary directory and mocks all Pixhost HTTP traffic; no NAS, qB, tracker or actual image upload is contacted. The runtime Docker image does not include Go; use a disposable test stage/environment, not a production NAS instance.

Builds support Linux amd64 (ordinary Intel/AMD desktops and NAS) and arm64 (64-bit ARM NAS). Building with compose directly on either platform uses native Debian media packages. For cross-building, use Docker buildx with the appropriate platform, for example `docker buildx build --platform linux/arm64 -f Dockerfile.nas --load -t ptmove-media-agent:0.3.1 .`; building the runtime Debian layer requires an arm64 builder or QEMU emulation. amd64 uses `--platform linux/amd64`. A multi-platform registry build can use `--platform linux/amd64,linux/arm64 --push` with your own registry tag. 32-bit ARM variants are not included. Cross-compiling the Go executable does not establish that ffmpeg/mpv work on a physical ARM NAS; validate a synthetic capture there before use.

Optional build arguments: `GOPROXY` defaults to `https://proxy.golang.org,direct`; `APT_MIRROR` defaults to `http://deb.debian.org` and expects a mirror base URL without `/debian` (e.g. `http://mirrors.cloud.tencent.com`). The Debian base initially has no CA bundle; use the signed HTTP package source to bootstrap certificates. Pixhost uploads always use the fixed official HTTPS API.

Prebuilt archives: load only the matching architecture with `docker load -i <archive>.tar.gz`. The arm64 archive uses tag `ptmove-media-agent:0.3.1-arm64`; on the ARM NAS run `docker tag ptmove-media-agent:0.3.1-arm64 ptmove-media-agent:0.3.1` before the standard Compose command. After editing `.env`, start without rebuilding using `docker compose --env-file .env -f compose.nas.yaml up -d --no-build`. The amd64 archive already uses the default Compose tag.
